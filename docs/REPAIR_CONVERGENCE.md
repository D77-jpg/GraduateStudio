# 自动验收修复收敛优化

## 问题

原流程集中验收后，把完整报告附加到模块提示中，多文件修复后再次全量验收。仅规范化整份报告的指纹，不能充分区分重复具体失败、日志噪声和修复引入回退。

## 新流程

1. 提取Vitest FAIL、Node ✖失败用例、构建/依赖根错误，忽略孤立普通错误日志；对路径/时间做稳定化。输出截断改为保留头和尾，诊断明确标记证据不完整。
2. 每轮选择一个失败检查，构建/语法前置问题优先；提供具体失败证据、相关路径、已通过项和禁止绕过的要求。
3. 计划不能跨出失败子工程或删除文件；应用前拒绝新增skip/todo/only、减少可识别断言、替换原build/test脚本。此规则不是完整语义证明，仍需执行测试与人工验收。
4. 修复后先定向执行原固定检查命令，不让模型生成任意执行命令。当前定向粒度为检查/测试套件，不是单个测试用例。
5. 定向通过仍执行全量验收。比较具体失败的已消除/新增/持续项目；发现此前passed检查回退则停止叠加并保留变更供核对，不自动回滚覆盖用户文件。
6. 证据完整且同一具体失败集合再次出现时停止重复生成，而不是设置固定轮数/调用额度。证据不完整不能宣称停滞已经得到证明。
7. 依赖清单/锁文件指纹不变且node_modules存在时复用成功安装状态；依赖变化或目录缺失才安装。

## 恢复兼容与边界

新增可选断点字段repairBaselineReport、repairFocusCheckId、dependencyFingerprints；旧任务继续使用已持久化的实施计划，不从头重写。新建修复计划使用新策略。正在暂停的项目不自动恢复，不发送真实模型请求。

不声称项目已可运行交付：测试可能存在错误、环境前置缺失及业务契约不一致，需基于真实项目再验证。当前保护只自动阻止明显绕过及检查级回退，不是逐行语义验证或自动事务回滚。

主要代码：src/lib/repair-diagnostics.ts、src/lib/repair-strategy.ts、src/server/agents/full-project.ts、src/server/agents/acceptance.ts。

# 完整生成效率优化

## 已观察问题

校园活动任务在90分钟内计入56次调用，完成4个模块及第5模块部分文件；49个成功的两文件批次累计96次文件变更。固定小批次、多模块重复修改入口与业务层、部署材料提前，导致耗时不匹配一键完整生成的体验。

## 本轮优化方向

1. 动态批次：按已有文件大小与预计输出量组合1至6个文件，仍保留逐文件计划覆盖与完整原文件保护。大文件单独处理，不把增加文件数等同于无上限输出。
2. 跨模块职责：基础层只做共享基础，不提前重复实现未来业务模块；规划与实现携带已完成范围及已有契约。部署与文档尽量后置，尊重实际依赖。
3. 上下文相关性：优先当前模块与相邻契约，避免每次机械塞入最后24个修改文件。
4. 批次边界持久化：新计划保存动态边界；已有未完成断点仍沿用原来的两文件边界，避免游标错位重复写入。
5. 技术栈匹配：添加Node后端真实工程验收；明确不支持的后端技术栈在模型调用之前提示，不等到最后失败。
6. 预算可授权追加：仅停止且预算耗尽的任务可通过明确确认追加60分钟、50次调用、100步，最多3次；不清零原消耗，不在页面打开时自动续跑。
7. 耗时可见：展示累计运行、调用耗时与剩余预算，接近上限提前提醒。

## 边界

保留已有生成代码和数据库，不自动恢复截图中的任务。旧任务当前未完成模块保持原批次布局，后续新模块使用动态批次；不重排已保存模块依赖计划，不跳过剩余需求。预算追加只增加额度，不清空累计消耗。

Node 测试支持严格的直接 `node --test` 或 Vitest；带自定义测试路径的未知脚本可能明确受阻并进入限额修复，不会冒充通过。JavaScript 语法检查最多128个文件、总60秒；测试仍不证明数据库业务端到端正确。运行中的暂停等待会计入墙钟预算，停止后的时间不增加；异常进程退出到恢复的间隔按已有保守策略计入。

全项目 TypeScript、ESLint 通过；19 个测试文件、218 个测试全部通过。测试使用模拟模型和注入执行器，覆盖动态/旧批次恢复、文件大小隔离、失败耗时记录、预算权限与控制器清理、Node 测试真实摘要以及技术栈预检。

本轮仅实现及回归验证，不触发真实模型费用，因此不承诺已实测的完成速度或固定倍数提速。质量检查、真实测试证据与断点冲突保护不能为了速度取消。
